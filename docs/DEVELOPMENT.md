## 1. 專案概覽與技術選擇

**目標**：一個網頁版的寶可夢開放世界。畫面與操作照《綠寶石》，對戰規則照最新世代（朱／紫），九大地區連在同一張地圖上，全部 1025 種寶可夢都遇得到。

**技術選擇與理由**

| 選擇 | 理由 | 代價 |
|---|---|---|
| 純 JavaScript，不用框架、不用建置工具 | 直接雙擊 `index.html` 就能玩，學習門檻最低；每個檔案就是一個系統，容易對照 | 沒有模組系統，靠 `<script>` 的順序與全域物件（見第 2 章） |
| 畫面 720×480 的 `<canvas>` | 是 GBA 240×160 的 3 倍，原版素材的每個像素剛好放大成 3×3 | 手機要另外縮放（第 8 章） |
| 世界用亂數種子生成 | 九個地區手工畫地圖不可能；同一個種子永遠生成同一個世界，存檔只要記種子 | 改生成程式會讓舊存檔的世界改變 → 需要「世界配置版本」（第 4 章） |
| 對戰照 Showdown 的流程 | Showdown 是社群公認最接近原作的對戰模擬器，有完整的招式與特性資料 | 要把它的資料格式轉成我們的 |
| 原版素材只在本機建置 | 圖塊、音樂是任天堂的著作，不能公開散布 | 線上版用內建的原創像素圖；所有程式都要能在「沒有素材」時運作 |

**一個重要的原則**：每個功能都要有「沒有原版素材時」的退路。例如 `Gen3.on` 為 false 時，建築用程式畫的像素圖、室內地圖退回選單、商店退回清單。線上版就是靠這個運作的。

## 2. 程式結構與載入順序

```
index.html          所有 <script> 依序載入
data/*.js           自動產生的資料（寶可夢、招式、道具、形態……）＋ towns.js（手工城鎮）
js/util.js          亂數（可設定種子）、雜訊、小工具
js/telemetry.js     遊玩紀錄（最早載入，才能接到之後所有錯誤）
js/data.js          屬性相剋、道具、地區、館主
js/mon.js           能力值、經驗值、進化
js/world.js         世界生成與繪製
js/ecology.js …     在 world.js 之後「擴充」World 的系統
js/battle.js、engine.js、battle_view.js   對戰
js/mega.js、zmove.js、late.js、doubles.js、ai.js   對戰的擴充
js/game.js          主程式：選單、存檔、主迴圈（最後載入）
```

**擴充模式（本專案最重要的寫法）**：後面的檔案用「包一層」的方式擴充前面的系統，而不是去改原本的程式。例如 `events.js` 要在世界生成後放置卡比獸：

```js
const _evGenerate = World.generate;
World.generate = function (...a) {
  const r = _evGenerate.apply(this, a);   // 先做原本的事
  this.placeEvents(...);                  // 再加自己的
  return r;
};
```

對戰的特殊能力（超級進化、Z 招式、極巨化）也是包在 `Battle.prototype` 上。好處是每個系統可以獨立讀懂、獨立關掉；代價是**載入順序很重要**——曾經因為特殊能力的檔案比戰鬥畫面早載入，戰鬥畫面後來覆寫了同名函式，包的那一層就不見了（第 10 章）。

**全域狀態**：`G` 是執行時的狀態（目前模式、按鍵、移動中的動畫），`G.state` 是要存檔的資料。規則很簡單：**會存進存檔的一定在 `G.state`，其他都不存**。

## 3. 資料管線：寶可夢、招式、譯名與原版素材

### 3.1 遊戲資料

- `tools/fetch_data.py` 從 [PokéAPI](https://pokeapi.co) 下載 1025 種寶可夢的種族值、屬性、升級招式、進化條件、中文名稱，轉成 `data/pokedex.js`、`data/moves.js`。
- `tools/fetch_showdown.py` 從 Pokémon Showdown 取得對戰用的招式資料（威力、優先度、旗標、附加效果）。
- 其他 `fetch_*.py` 各自負責形態、招式學習器、Z 招式、培育……

**為什麼要轉成 `.js` 而不是讀 `.json`？** 直接開啟 `file://` 時，瀏覽器不讓網頁用 `fetch` 讀本機檔案，但 `<script src>` 可以。所以資料檔都寫成 `window.POKEDEX = {...}`。

### 3.2 中文譯名

所有名稱（地名、人名、道具）都到 [神奇寶貝百科（52poke）](https://wiki.52poke.com/) 查證。這一步不能省：例如青綠的姊姊叫「奈奈美」，不是直覺會猜的名字；阿羅拉的隊長「茉莉」、伽勒爾的「瑪俐」「赫普」都是查過才寫進去的。

### 3.3 原版素材（pokeemerald）

[pret/pokeemerald](https://github.com/pret/pokeemerald) 是《綠寶石》的反組譯專案，裡面有原作的圖、地圖與音樂。`tools/build_assets.py` 把它們轉成遊戲用的格式：

- **GBA 的圖是「圖塊＋調色盤＋圖塊表」**：一張 `tiles.png` 存 8×8 的小圖塊（每個像素是 0–15 的顏色編號），`.pal` 存顏色，`map.bin` 存每一格用哪個圖塊、哪個調色盤、要不要翻轉。`tools/gen3_tiles.py` 的 `render_tilemap` 就是在模擬 GBA 的繪圖硬體。
- **地圖由 16×16 的「metatile」組成**：每個 metatile 由兩層、各 4 個 8×8 圖塊組成，還有屬性（行為：草叢、水、櫃台……；圖層類型：哪一層畫在人物上方）。
- **室內地圖**（`tools/build_interiors.py`）：讀地圖的區塊資料，碰撞取自每格的 collision 位元，NPC 與出口取自 `map.json`；依圖層類型把畫面拆成「人物下方」與「人物上方」兩張圖，所以櫃台會擋住主角的腳。
- **檢查素材的正確性**：建置時會順便檢查。例如道館地圖要確認「從入口走得到館主」，推石頭的洞窟要用搜尋確認解得開（第 9 章）。

## 4. 世界生成：一張可重現的大地圖

### 4.1 決定性（Determinism）

`World.generate(seed, homeRegion, worldVer)` 用 `mulberry32(seed)` 當亂數來源，**整個生成過程不呼叫 `Math.random()`**。同一個種子永遠得到同一個世界，存檔只要記種子。這也是為什麼新增功能時要很小心「亂數的使用順序」：多抽一次亂數，後面所有東西的位置都會變。

### 4.2 生成步驟

1. **地形**：每一格用分形雜訊（`fbm`）算出高度、濕度、溫度，再加上「離哪個地區的中心最近」（`landInfo`，依距離加權各地區的氣候）。依數值決定是水、沙灘、草叢、山、雪地……
2. **城鎮**：每個地區 10 座（家鄉、8 座道館、聯盟），依離家鄉的距離決定第幾座道館。
3. **道路**：城鎮之間挖路，經過水面變成橋。
4. **蓋章**：城鎮內部、建築、門。關都的重要城鎮用 `data/towns.js` 的字元地圖手工配置。
5. **地標、傳說、事件、隱藏道具**：放在指定城鎮附近、走得到的地方。

### 4.3 世界配置版本（worldVer）——為什麼需要它

**問題**：玩家的存檔只記種子。如果我改了生成程式（例如修正道館順序），同一個種子會生成不同的世界，玩家已經拿到的徽章就對應到錯的城鎮。

**解法**：存檔記錄 `worldVer`，生成時依版本走不同的規則：

```js
const gymIdx = this.worldVer >= 2 ? (order.length - 2) - k : k - 1;   // 第 2 版修正道館順序
if (this.worldVer >= 3) this.stampDesign(...);                        // 第 3 版手工城鎮
if (lm.ver && lm.ver > this.worldVer) continue;                        // 新的地標只在新版出現
```

目前到第 7 版（道館順序 → 手工城鎮 → 道路訓練家 → 合眾～帕底亞地標 → 對戰塔 → 地形平滑與城鎮邊界）。**測試會鎖住舊版的地形雜湊**，有人不小心改到舊版的生成，測試就會失敗。

### 4.4 等級曲線

野外等級 = 地區等級帶 × (離家鄉的進度 k)^1.35。原本是 k^1.6，自動遊玩機器人量測發現中期道館比沿路野外高 7～10 級，要練等 50～100 場；改成 1.35 後差距 3～6 級（第 9 章）。

## 5. 繪製：圖塊、自動拼接、地形交界與室內

### 5.1 自動拼接（autotile）

水、沙灘、山這類地形的邊緣要用不同的圖塊。做法是看上下左右（與四個角）是不是同一種地形，算出一個 8 位元的遮罩（`Gen3.auto` 的 `mask`），用遮罩查「學習來的」圖塊表。這張表是建置時從綠寶石的真實地圖統計出來的：哪種鄰居組合在原作裡用哪個圖塊。

### 5.2 依環境換色與交界

綠寶石沒有「雪地裡的道路」這種圖塊（原作的道路都在草地旁）。解法是在執行時換色：

- 雪地裡的道路：疊一層淡白色（`source-atop` 合成）。
- 地形交界：等級高的地面（雪 > 沙漠 > 岩地 > 草地 > 沙灘）在交界處蓋到旁邊的格子，用 `destination-in` 遮罩做出鋸齒邊。
- 水邊：靠岸的一側畫浪花線。

> ⚠️ **重要教訓**：最初的換色是用 `getImageData` 讀像素再改顏色。直接用 `file://` 開啟時，瀏覽器把每張圖片當成跨來源，讀像素會丟出 SecurityError，畫面畫到一半就停住。改成只用畫布合成、不讀像素才解決（第 10 章）。

### 5.3 人物的前後關係

人物（主角、訓練家、野生寶可夢、傳說）放進同一個陣列，依 y 座標排序後依序畫，下方的蓋住上方。站在草叢裡時，再把草叢的下半部畫在主角上面。

### 5.4 室內

室內用另一套很小的引擎（`js/interior.js`）：背景圖、碰撞字串、NPC 清單、出口、往下一間的門。主角在室內時，世界座標停在門口——所以在室內存檔、讀檔會回到門口，不需要額外的存檔欄位。寶可夢聯盟是「房間鏈」：大廳 → 四天王 ×4 → 冠軍，進去後門會關上。

### 5.5 防錯

每個物件（每一格地形、每棟建築、每個人物）各自 `try/catch`，一個出錯只略過它並記錄位置，不會讓整個畫面停住。

## 6. 對戰引擎：照 Pokémon Showdown 的回合流程

### 6.1 回合流程

```
選擇行動（雙方）→ 換人與道具先處理 → 依優先度、速度排序招式 →
  每個招式：能不能動（睡眠、麻痺、畏縮）→ 命中判定 → 傷害計算 → 附加效果 → 倒下判定
→ 回合結束：天氣、場地、殘留傷害、計時器
```

`engine.js` 的函式名稱刻意對應 Showdown（`runMove`、`useMoveOn`、`calcDamage`），遇到規則問題可以直接對照 Showdown 的原始碼。

### 6.2 傷害公式

```
基礎 = floor(floor(floor(2 × 等級 / 5 + 2) × 威力 × 攻擊 / 防禦) / 50) + 2
傷害 = 基礎 × 天氣 × 會心 × 亂數(0.85–1) × 屬性一致 × 相剋 × 灼傷 × 其他修正
```

特性與道具用「修正函式」掛在各個階段（威力修正、攻擊修正、最終修正），這也是 Showdown 的做法。

### 6.3 特殊能力（太晶化、超級進化、Z 招式、極巨化）

每一種都是獨立檔案，包在 `Battle.prototype` 上。一場對戰只能用一種（`gimmickUsed`）。戰鬥中選招式時，上方的「特殊能力列」列出能用的與不能用的原因——這是使用者回報「找不到在哪裡」之後加的。

### 6.4 雙打

雙打沿用單打引擎：每次行動前把「我方／對手」切換成正在行動的那一對（`ctx`），每隻寶可夢有自己的狀態。全體招式要分清楚：`allAdjacentFoes`（只打對手）與 `allAdjacent`（地震、衝浪，連隊友也打）。行動順序每次行動後用當下的速度重新排序（第八世代起的規則）。

## 7. 訓練家 AI 與野生寶可夢的習性

### 7.1 三層 AI（`js/ai.js`）

| 層 | 對象 | 會做什麼 |
|---|---|---|
| 1 | 一般訓練家 | 估算傷害，選打得最痛的；打得倒優先 |
| 2 | 館主 | ＋被剋制又撐不住時換人、看時機用異常狀態（避開免疫）、天氣對自己有利才用、回復道具 |
| 3 | 四天王、冠軍 | ＋預測玩家最強的招式先換人、安全時強化、太晶化的時機 |

**關鍵設計：傷害估算和實際計算分開**。實際的 `calcDamage` 會擲會心、有副作用（例如消耗雷射聚焦），AI 不能直接呼叫。所以 AI 有自己的 `AI.est`，不擲骰、不改狀態，也能估算還在後備的寶可夢。

### 7.2 野生寶可夢的習性

`Wild.of(物種)` 決定習性：代表性的物種查表（卡比獸定點、凱西膽小），其他依屬性與種族值推定（幽靈 → 夜行、很慢或很重 → 定點、格鬥或龍 → 兇猛）。地圖上依習性移動：兇猛的會衝過來、膽小的逃跑、成群的跟著帶頭的走。

## 8. 遊戲系統：存檔、帳號、介面、觸控

### 8.1 存檔

- **驗證**：讀檔時檢查每個欄位，無法修正的錯誤（物種不存在）拒絕，可以修正的（努力值超過上限）直接修正。
- **備份**：寫入前把上一份有效的存檔保留為備份，主存檔壞掉時可以恢復。
- **格式版本與遷移**：存檔有 `v`，讀檔時依序跑 `Game.MIGRATE[1]`、`[2]`……升到目前版本，只補欄位、不刪資料。比遊戲新的存檔會明確拒絕。
- **測試**：完整的中後期存檔「匯出 → 匯入」要完全相同。

### 8.2 帳號

帳號存在瀏覽器（`localStorage`），密碼用 PBKDF2-SHA256（12 萬次、隨機 salt）雜湊後才儲存。每個帳號有自己的存檔位置；訪客沿用原本的位置，舊存檔不受影響。儲存層集中在 `Account.store`，要接雲端只要換掉這四個函式。

### 8.3 介面

所有選單共用一個「按鍵堆疊」（`UI.pushKey`）：最上層的選單接收按鍵，關掉時彈出。對話框、選項、清單、綠寶石樣式的各種畫面都用這個機制，所以不會兩個選單同時吃到按鍵。

> 小心 CSS 的優先順序：`body.gen3 #choices { bottom: 162px }` 比 `#choices.title-menu { bottom: 70px }` 更具體，素材載入後標題選單就被推到畫面中間（第 10 章）。

### 8.4 觸控與手機

`fit()` 依螢幕方向決定版面：直向時遊戲在上、掌機樣式的按鍵在下；橫向時按鍵疊在兩側。十字鍵在野外設定「走路方向」，在選單裡改成送出方向鍵事件（按住自動連按）——因為選單是聽按鍵事件的。

### 8.5 遊玩紀錄（Telemetry）

`js/telemetry.js` 最早載入，接住所有錯誤（含 Promise）、量測 FPS 與耗時、記錄最近的遊玩事件與對戰統計。玩家回報「某些地方畫面怪怪的」時，請他下載紀錄檔就知道是哪個物件、哪個位置出錯。

## 9. 測試：怎麼確定改了東西沒有壞掉

### 9.1 引擎回歸測試（`tests/engine_test.html`）

約 380 個測試，涵蓋對戰機制、存檔、世界生成、城鎮、室內、AI、遊玩節奏。用瀏覽器開啟就會跑。幾個值得學的技巧：

- **固定亂數**：`U.seed(42)` 讓機率性的結果可以重現。
- **固定外部狀態**：天氣依現實時間變化，測試一開始先 `Weather.force('clear')`。
- **替換互動**：把 `UI.choose` 換成固定回答的函式，就能測「問玩家要不要做某事」的流程。
- **鎖住不該變的東西**：用雜湊鎖住舊版世界的地形。

### 9.2 冒煙測試（`tests/smoke.html`）

單元測試一次只測一個機制，但很多錯誤出在「接起來」的地方（例如戰鬥結束後回到野外時重畫地圖）。冒煙測試用遊戲本身的流程，幾秒內走過：新遊戲 → 進出室內 → 單打 → 雙打 → 存檔與讀檔 → 雲端同步失敗（用假的 `fetch` 回傳伺服器錯誤）→ 畫面提示。

- 頁面由 `index.html` 產生（路徑前面加 `../`，最後換掉 `Game.title` 並載入 `smoke.js`）；新增遊戲的 js 檔時也要加進去。
- 和遊戲共用 `localStorage`（本機的 file:// 網頁共用同一份），所以開始前備份 `pkmn` 開頭的資料、結束時還原，不會蓋掉玩家的存檔。

### 9.3 自動遊玩機器人（`tests/playthrough.html`）

機器人透過遊戲本身的流程從新遊戲打到關都冠軍：打路上的訓練家、在合適的草叢練等、挑戰道館、連戰四天王。它找出了很多單元測試抓不到的問題：

- **道館順序是反的**：第一座道館在地區最遠的地方，機器人在第一座道館前就卡住了。
- **節奏**：每座道館要練多少場、路上有沒有訓練家（原本平均 38 格道路才 1 位）。

> 機器人本身也會有錯：一開始學新招式時永遠忘記第一招（噴火龍 Lv.53 還在用火花），還會一直用大爆炸讓自己拿不到經驗值。測試工具也要檢查。

### 9.4 用搜尋證明「解得開」

推石頭的洞窟用廣度優先搜尋走遍「玩家位置 × 石頭配置」的所有狀態（`tools/check_caves.py`），確認從入口推得到終點。原本選的一個房間不用推石頭就走得到終點——那就不算解謎，換掉。測試還會把搜尋到的解法用遊戲本身的移動實際走一遍。

### 9.5 掃描整張地圖

畫面相關的錯誤用掃描找：在整張地圖上每 4 格繪製一次（約 3.5 萬次），收集所有錯誤與位置。

## 10. 經驗教訓：真實的錯誤與找出原因的過程

| 現象 | 真正的原因 | 怎麼找到的 | 學到什麼 |
|---|---|---|---|
| 走到某些地方畫面停在一半、物件消失 | 用 `getImageData` 讀圖塊像素；`file://` 開啟時圖片算跨來源，丟出 SecurityError | 測試環境加了允許讀檔的參數所以沒發現；用和玩家相同的環境掃描整張地圖才重現 | **測試環境要和使用者一樣**；能不讀像素就不讀 |
| 返回標題後選單跑到畫面中央 | CSS 選擇器的優先順序：素材載入後的規則蓋掉標題選單的位置 | 比較「第一次開啟」與「返回標題」：差別在素材載入了沒 | 第一次正常、第二次壞，先找「兩次之間有什麼不同」 |
| 對手寶可夢先以小尺寸出現 | 換圖時，圖片在載入、放大之前是看得見的 | 觀察是「先小後大」→ 尺寸是載入後才設定 | 非同步載入的東西，完成前先隱藏 |
| 第一座道館要練好幾百場 | 道館編號依「離家由遠到近」 | 自動遊玩機器人卡在第一座道館；量測各道館附近的野外等級 | 用實際玩一次的方式驗證，比讀程式快 |
| 特殊能力的效果消失 | 載入順序：後載入的戰鬥畫面覆寫了包好的函式 | 檢查函式是不是被包過 | 擴充模式要注意載入順序 |
| 快龍只能用龍之舞 | 測試存檔讓牠帶了講究頭帶，用過龍之舞就被鎖住 | 讀規則：講究系道具會鎖招 | 使用者回報的「錯誤」可能是規則，要讓介面說明原因 |
| 雪地上的道路很突兀 | 原作沒有雪地道路的圖塊 | 看截圖 | 原作沒有的組合要自己補（換色、交界） |
| 測試在網頁伺服器上卡住 | 無頭瀏覽器的虛擬時間會等網路請求 | 改用 file:// 跑同一份檔案就正常 | 先分辨是「程式的問題」還是「測試工具的問題」 |

**除錯的一般步驟**：重現 → 縮小範圍（哪個位置、哪個物件、第幾次）→ 找出「正常與不正常之間的差別」→ 修正 → 加一個會在問題重現時失敗的測試。

## 11. 開發流程：里程碑、回報、版本控制

1. **里程碑**：[PROGRESS.md](../PROGRESS.md) 列出規劃。最後一輪的規劃來自一份外部檢查，建議從「功能廣度」轉向「可完整遊玩、各地區有特色」，分成四個里程碑：穩定性 → 一個真正完整的關都 → 策略與生態 → 擴展內容。
2. **每次更新都記錄**：在 [DEVLOG.md](../DEVLOG.md) 最上方寫一筆（做了什麼、為什麼、測試結果），同一個提交推上 GitHub。
3. **使用者回報 → 修正的循環**：每個回報都先找到真正的原因（見第 10 章），修正後加測試，再寫進 DEVLOG。很多重要的改進（室內地圖、地形交界、手機版）都是從回報開始的。
4. **相容性**：改存檔格式要升 `SAVE_VER` 並加遷移；改世界生成要升 `WORLD_VER` 並讓舊版沿用舊規則。
5. **提交訊息**：第一行說做了什麼，下面列出重點與測試數量。

## 12. 模組化：從傳統腳本到 ES module、Vite 與 Preact（`vite-esm` 分支）

原本的程式是 index.html 依序載入的 60 個傳統腳本，檔案之間靠全域變數互相呼叫，載入順序就是執行順序。改成 ES module（`import`／`export`）時遇到的問題與做法：

1. **自動找出依賴**：`tools/esm_convert.cjs` 用 espree 解析每個檔案、eslint-scope 分析作用域，得到「這個檔案宣告了什麼」與「用到別的檔案的什麼」，自動加上 `import { … } from './x.js'` 和 `export { … }`。先只分析、列出問題（寫入別的檔案的變數、重複宣告、隱含的全域變數），沒有問題才改寫。
2. **執行順序**：ES module 會先執行被 import 的模組。傳統腳本裡「比較早的檔案在執行期才呼叫比較晚的檔案」（例如 util.js 用到 game.js 的 `G`）很常見，改成 import 之後會形成循環，執行順序整個亂掉（模擬的結果是 late.js 在 engine.js 之前執行，包裝 `Battle.prototype` 的順序就錯了）。解法是讓**每個 import 都指向比較早的檔案**：
   - 這種「往後參照」的單例物件（`G`、`Game`、`UI`、`Story`……共 26 個）先在最早的 `js/core.js` 宣告成空物件，原本的檔案用 `define(X, {...})` 把內容（含 getter）填進去，呼叫的地方完全不用改；
   - 往後參照的函式手動搬到比較早的檔案（`md`、`newVol` → `js/movedata.js`，`monSprite`、`playCry` → `js/sprites.js`）；
   - 工具模擬 ES module 的執行順序，確認和原本的載入順序完全相同才改寫。
3. **改寫之後才發現的差異**：資料檔 `data/towns.js` 用 `const TOWN_DESIGNS`（傳統腳本是全域，模組裡變成私有）；`document.currentScript` 在模組裡是 null；測試頁裡的 `<script>` 要改成 `type="module"` 才會在遊戲模組之後執行。全部靠測試抓出來（引擎 543、冒煙 17、實際遊玩 17）。
4. **Vite**：開發伺服器（`npm run dev`）與打包（`npm run build`）。打包後 JS 從原本合併的 1.9 MB 變成 1.37 MB（gzip 425 KB）；圖鑑說明在打包時拆成 `data/dex_text.js`、頁面載入後才下載（原本 `tools/build_web.py` 做的事改成 Vite 外掛）；綠寶石素材在執行期才用網址載入，打包後原樣複製。
5. **Preact**：介面逐步改成元件。第一個是設定畫面（`js/ui/option_menu.jsx`），DOM 結構和 class 與原本相同，樣式不用改。遇到的差異：Preact 的 `useEffect` 在下一次繪製才執行，冒煙測試打開畫面後馬上按鍵就收不到；改用 `useLayoutEffect`（在 `render()` 裡同步執行），行為才和原本一樣。

> 💡 這次的重點：大規模的機械式改寫交給工具（解析、模擬、檢查），工具先「只分析不改寫」；改寫後用原本就有的測試確認行為不變，截圖和原本的版本並排比較。
